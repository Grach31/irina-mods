# Fashion Daily and Style Time Machine publication

Both sections use the existing authenticated moderator session, bot credentials and Stambo.i destination through `myspace-publish`. They never create a Moda draft, invoke GPT on click, start a workflow or publish automatically. Anonymous/read-only clients cannot enqueue a send. Internal diagnostics force the preview action, regardless of supplied action data.

Fashion Daily uses the prepared plain `telegram_text`, or its existing GPT-written title/summary/why for older items, with photo credit and source appended by the server. A moderator can edit the main text, then regenerate the exact preview before confirming. History is read-only and preserves the displayed title, year/period, summary/description, Then/Now text, all distinct photos and their full captions, credits and sources. Long content splits into photo/album and complete text messages; HTML entities and surrogate pairs are not split. A photo is mandatory for both.

`editorial.ts` loads the selected item from current main and deployed Pages and rejects version skew. Every photo is downloaded and format/size checked before preview and again before claiming publication. The approved revision covers source fields, exact message plan, and photo byte hashes. Clients cannot supply photo URLs, credentials or a destination. Changed source/text/photo requires a fresh preview.

`supabase/editorial/publications.sql` is the canonical server-only state/RPC definition, applied after the existing notification schema. The independent RLS-protected table keys records by section and source ID. No browser role can read it or execute the state RPCs. The existing Moda publication table and its decisions remain unchanged.

Claims use an advisory lock and an attempt UUID. Each accepted Telegram result is checkpointed before the next message is sent. Retrying a lost database acknowledgement is idempotent; it never resends Telegram. A definite Telegram rejection is retryable at the unsent part under the same approved plan. A changed partial plan requires manual review. A timeout, malformed success, or unavailable acknowledgement storage leaves publishing/uncertain state and blocks automatic retries. Inspect the real channel before any manual recovery; never clear a claim blindly.

`editorial-publish.js` shows the actual planned photo/caption/text messages in a native modal dialog. Preview never sends. Input edits invalidate confirmation until a new preview is built. Only the explicit confirmation button sends; duplicate clicks are blocked. Successful publication disables the section's button and displays the actual post link; catalog content remains available. State is synchronized in one batched request rather than one request per card. Sign-in completion reveals previously rendered moderator controls.

Validation: Node builder/transport tests; rolled-back service-role SQL checks in `tests/editorial-publication.sql`; isolated UI checks in `tests/editorial-publish-dom.cjs` (set HAPPY_DOM_PATH). Production diagnostics support `action:diagnostics, space:fashion|history, id` under the existing internal worker bearer and only download/read the material. They never send or create publication state. Actual channel publication is tested through the user's final confirmation.
