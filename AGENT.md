# Stambo.i / My Space — технический регламент
Обновлено: 13.11.2026. Рабочий репозиторий: `Grach31/irina-mods`, ветка `main`.

## Назначение и приоритет
Этот файл фиксирует **технические контракты, форматы данных, проверки и границы ответственности**. Он не задаёт расписание, ежедневные редакционные квоты или новые задания для публикации. Единственный источник текущего редакционного плана — активная задача ChatGPT **«Единая GPT-редакция — Stambo.i и My Space»**. При расхождении редакционных указаний приоритет у неё; требования формата и безопасности из этого файла обязательны, если совместимы с работающим кодом.

## Компоненты и ответственность
- **GPT-редакция**: выбирает сюжеты и товары, проверяет факты/актуальность/повторы/изображения и права, пишет материалы и сохраняет проверенные JSON/разрешённые медиа в GitHub. Не инициирует публикацию в Telegram без явного одобрения.
- **GitHub**: источник хранимых данных. `drafts/*.json` — черновики Stambo.i; `state/state.json` — технические статусы; `miniapp/*.json` — редакционные витрины My Space.
- **My Space / Moda**: отображает общую очередь черновиков и предоставляет авторизованному модератору интерфейс решений. Не подменяет подтверждение публикации простым сохранением JSON.
- **GitHub Actions / Telegram-бот**: транспорт, формирование медиа, учёт статусов и исполнение **только явно одобренной** публикации. Бот не ищет товары, не пишет редакционные тексты, не выбирает новости и не проверяет факты повторно. Перед отправкой он вправе технически проверить формат/доступность медиа, разрешение на публикацию и отсутствие повторной отправки.
- Различать состояния: **коммит GitHub ≠ готовый каталог Pages ≠ отображение Safari ≠ Telegram-доставка ≠ одобренная публикация**. Каждое подтверждать отдельно; отсутствие подтверждения обозначать явно.

## Файлы и обновления
- `drafts/<id>.json` — отдельный черновик; **не создавать индексный JSON внутри `drafts/`**, бот может принять его за публикацию.
- `data/candidates.json` — кандидаты товаров: `name, price, url, img, shop, kind`; `data/sheets/<магазин>.jpg` — контактные листы с номерами, совпадающими с индексами кандидатов.
- `data/requests.json` — запросы пользователя; `state/state.json` — транспорт и модерация. Во время обычной редакции GPT читает, но не перезаписывает `data/`, `state/`, `bot/`, `.github/workflows/`.
- `miniapp/fashion-daily.json` — новости, `miniapp/fashion-archive/YYYY-MM-DD.json` — архив выпуска, `miniapp/style-time-machine.json` — история моды, `miniapp/reels-studio.json` — идеи видео, `miniapp/trend-radar.json` — тренды. Использовать **фактические существующие схемы**, не заменять их произвольной структурой. Сохранять другие записи, российский/международный потоки, стабильные ID и уникальные URL.
- `scripts/build_miniapp_catalog.py` строит публичный каталог `miniapp/catalog.json` для Pages. Новый черновик текущего редакционного дня без статуса может появиться в Moda со статусом `queued` **до** Telegram-доставки; это не разрешение на публикацию. Статусы обработки берутся из `state/state.json`. Появление в Safari проверять после обновления Pages.
- Изменять только файлы, необходимые текущему редакционному заданию. Не изменять код, workflows и права доступа в обычном контентном цикле.

## Формат черновиков Stambo.i
Файл `drafts/<id>.json`: `id` совпадает с именем файла, уникален (предпочтительно `YYYY-MM-DD-краткая-тема`); `slot: null`; `text` — подготовленный текст; `daily` — согласно реальному заданию. Для товарной подборки `type: "picks"` и массив `items` из реальных товаров:

```json
{
  "id": "2026-11-13-mix-knit",
  "type": "picks",
  "daily": true,
  "slot": null,
  "items": [
    {"name": "Наименование товара", "price": 7999, "url": "https://example.com/product", "img": "https://example.com/product.jpg", "shop": "Название магазина"}
  ],
  "text": "Оригинальный HTML-текст для публикации"
}
```

- Смешанная подборка содержит товары нескольких разрешённых магазинов; подборка одного магазина — товары этого магазина. Конкретное количество выпусков задаёт **задача GPT**, а не этот файл. **Wildberries не использовать**.
- Каждый `url`, цена, название, магазин и `img` должны соответствовать **одному и тому же товару**. Не выдумывать наличие и цены. Проверять повторы товаров/артикулов за предыдущие 14 дней и визуально просматривать контактные листы `data/sheets/*.jpg`, а также готовые `drafts/img/*.jpg`.
- Для каталогов товаров **фото каждой вещи обязательно**. При отсутствии или несовпадении изображения заменить товар проверенным кандидатом; не выпускать подборки с пустыми фотографиями.
- `text` — короткий оригинальный русский текст, товары с проверенными ссылками. Не приписывать автору личный опыт или покупки. Для Telegram HTML использовать поддерживаемые `<b>`, `<i>`, `<a href="...">`; экранировать спецсимволы. Учитывать ограничение подписи к фото Telegram (1024 символа), не обрезать ссылки и смысл.
- Служебные `hold: true` и предпросмотры применять только если их поддерживает действующий код. Не снимать `hold`, пока обязательные фотографии и итоговое превью не проверены.
- Старые типы `looks`, `news`, `album`, `item`, `history` могут встречаться в архиве и технически поддерживаться кодом. **Само их существование не означает, что нужно ежедневно создавать новые `looks` или Telegram-новости.** Дополнительные материалы — только по действующему заданию или отдельной просьбе.

## Стандарты фотографий My Space
**Fashion Daily**
- Проверять тематическое соответствие, источники и права. Предпочитать релевантное фото конкретной новости и указывать происхождение. Поля `image`, `image_url`, `image_rights`, `image_source` заполнять согласно текущей схеме и реальному основанию использования.
- **Исключение:** если после поиска нет подходящего доступного изображения с допустимыми условиями использования, новость **можно выпускать без фото** с текстовой редакционной обложкой. Не блокировать подтверждённую новость и не подставлять постороннюю фотографию.

**Style Time Machine**
- Для **каждой новой карточки** обязателен минимум один соответствующий действующий объект `photos`: `url`, `caption`, `credit`, `source_url`, с проверенным происхождением и допустимыми условиями использования.
- Если для темы нет подходящей фотографии, **самостоятельно выбрать другую проверенную историческую тему с фото**. Не выпускать новую карточку без изображения и не отказываться от всего выпуска только из-за первоначальной темы.
- Отличать современную фотографию исторического предмета от архивного снимка события/года; не вводить читателя в заблуждение подписью.

**Stambo.i / Moda**
- На каждой товарной карточке фотография **именно указанной вещи из магазина**; проверять, что исходный товар и итоговое JPG совпадают. Пустые фото не допускаются.
- Для исторических или специальных медиа при отдельном запросе — использовать проверенные разрешённые изображения, корректную атрибуцию, без нерелевантных замен.

**Общее**
- Проверять: URL доступен, изображение действительно загружается, соответствует тексту, не обрезано/не искажено, не имеет ложных подписей. Сохранять локальные копии **только при наличии прав**, если это повышает устойчивость. Права на просмотр чужой страницы не равны праву на копирование изображения.
- После GitHub-коммита проверить каталог и фактическое отображение в Safari, если такая проверка доступна. Не выдавать наличие `image_url` в JSON за гарантию, что фото показано на iPhone; сбои hotlink фиксировать и устранять при возможности.
- Если отдельный раздел не готов, продолжать независимые разделы; ясно сообщать о реальной блокировке.

## Техническая доставка и модерация
- Не считать `queued` доставленным. `sent_at`/соответствующий статус в `state/state.json` подтверждают лишь записанную доставку; **не** факт просмотра человеком или публикации.
- Публикация возможна только после **явного авторизованного одобрения**, с защитой от дублей по `id`. Никакой автоматической публикации по расписанию или из-за появления файла.
- Для товарных подборок с несколькими вещами — отдельные фото в Telegram-альбоме с общей подписью, не обязательный коллаж 2×2. Соблюдать ограничения Telegram по количеству медиа и подписи.
- Проверять техническую доступность медиа перед транспортом. При сбое указывать точную причину, не создавать фиктивные статусы и не дублировать уже отправленный материал.

## Контроль качества перед завершением
1. Проверить факты, источники, даты, права изображений, сопоставление фото и текста, отсутствие повторов.
2. Проверить структуру и парсинг JSON, уникальные ID, неповреждённые старые материалы, существующую схему.
3. Сохранить независимые готовые материалы в GitHub, получить commit SHA; ошибки одной рубрики не блокируют остальные.
4. По возможности проверить статус развёртывания Pages и фактический результат в My Space; транспорт Telegram — отдельно. Не заявлять непроверенное успешным.
5. Не публиковать без согласования, не править транспортный код в обычном редакционном запуске.
